## 2. 源码确认的调用链

### 2.1 现有 Sensor 路径不适合直接承载原文

`Context.register_runtime_observation_sensor()` 返回的句柄只提交观察事实。`runtime_sensor.py` 的材料校验拒绝 `text`、`content`、`prompt`、`visible_reply_material` 等键，并限制长字符串和换行。

当前直播空闲机会经 `proactive_schedule_due` 提交，后面仍由主动策略决策。把故事改个字段名塞进这个入口，既没有建立仅表达契约，也没有满足“不经过随机话题 Policy”的要求，因此不能作为打通方案。

### 2.2 普通直播输入还不能强制仅表达

`stream_platform.py` 的 `submit_live_item()` 提交普通输入并等待 OLV 终态，没有正式的仅表达参数。普通 Pipeline 的 `prepare_parallel_turn_control()` 仍会创建 Core Router 任务。

因此，给消息附加一句“不要调用工具”，或自定义一个未被 Core 识别的字段，都不能证明 Router/执行器已经被跳过。本次未用此方法向正在运行的系统注入故事。

### 2.3 Core 存在可复用的纯表达实现，但不是现成的共读入口

`InteractionMiddleware.handle_runtime_observation()` 的实现明确不走普通 Core 路由。`PersonalRuntimeManager.submit_runtime_observation_event()` 提供会话接收和运行上下文，OLV 也有 Runtime 输出和终态管理能力。

但该实现是内部观察/主动表达链路，输入使用 `visible_reply_material`。它不等于“插件通过 Core 队列提交原文、生成评论、获得明确结果”的正式接口；评论意图、原文与前情的区别、明确静默以及接收结果都需要补齐。不能直接调用私有方法来掩盖这个缺口。

本项为源码追踪结论，没有进行真实模型、语音或桌宠调用，不能标记为端到端通过。

## 3. 必须先补齐的部分

1. **Core 受控仅表达入口**：保留输入来源和会话归属；在创建 Router/执行器前分流，明确评论意图、公开上下文及材料边界；不经过随机主动话题 Policy。
2. **接收与终态结果**：区分忙碌未接收、已接收、明确静默、发布/播放完成、失败和结果不明；返回可关联的 Core/播放轮次 ID。
3. **展示与进度模块**：现有代码尚未实现材料展示、主展示端确认及翻页规则；HTML/SSE 边界通过不能代替这些功能验收。
4. **OBS 访问方案**：普通宿主 API 需要登录；还要实现受限展示凭据，实际验证静态资源、SSE、确认请求及 OBS 刷新/重连。
5. **真实播放条件**：接口实现后成套同步源码并加载，连接正确的 AG99 会话，再做一段材料的真实评论、TTS、动作和终态验收。当前源码/部署不一致，不能把正在运行的旧链路日志作为新源码通过的证据。

## 6. 实施后的隔离验收

- 通过真实的 AstrBot 登录和 AG99live 控制台接口验证预览、保存、开始和状态 SSE。未登录请求返回 401。
- Edge 打开复用的字幕页，先后渲染两段原文并各自发出展示回执。结束场次后字幕页收起原文，较早版本的回执返回 409。
- 本地表达模型生成针对原文的评论，独立动作模型交付动作数据，OLV 测试端收到同轮输出。日志中该轮的路由模式为 `none`、Core 执行器耗时为 0。
- 流式测试收到文本增量和动作更新。非流式测试在空闲时自动触发，使用测试 WAV 验证同段评论、音频和动作的绑定。
- 播放终态由 OLV 协议测试端提供。测试确认终态前评论保持进行中，忙碌请求返回 `busy`，符合展示停留时间后才推进至下一段。
- 提交前使用三个仓库的暂存源码复验。当前带版本字段的流式协议通过，另一个共读浏览器打开并关闭时，主展示端的回执继续有效。

正式直播实例的 B 站输入、OBS 采集、TTS 和 Live2D 实际播放仍待现场验收。
